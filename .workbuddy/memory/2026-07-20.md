
## M11 营销中心前端（优惠券/限时活动/邀请签到）

用户指令「营销」。**先核实现状** —— 发现后端营销已完整落地（6 张表 + controller + 55KB service，
非本轮我做的），缺口只是前端。E2E **14/14**，联跑 **47/47** 全通。

### 三页设计要点

**优惠券（B-64）**
- 券不提供删除入口 —— 已核销订单仍引用它，删了历史订单悬空。只有「停用/启用」。
- **编辑时券码输入框不渲染**（DTO 里 code 是 optional + 更新留空=不改）。改券码等于让用户手里的券集体失效。
- `value` 语义随类型而变：`full_cut`/`fixed` 是减免**分**，`discount` 是折扣**万分比**（8500 = 85折）。
  UI 上折扣显示「8.5 折」、满减显示「¥5.00」——混用会让运营填错。

**限时活动（B-65）**
- payload 字段随类型切换，只提交当前类型需要的字段 —— 混着提交会让改类型后残留数据意外生效。
- **状态 active 但不在时间窗内 → 标「未在窗内」**。这是最容易误判的状态：配置看着生效了，用户端却看不到。

**邀请与签到（B-66/67）** —— 单条全局规则，用表单直接编辑比列表+详情更直接。

### 踩到的坑

**① Prisma Client 没重新生成 → 营销全部接口 500**
现象：`Cannot read properties of undefined (reading 'findMany')`。
我上一轮生成交易域 Prisma Client 时，营销模型还没进 schema。后来营销表建好了但我没重新 generate。
**排查弯路**：先怀疑依赖注入（`design:paramtypes` 正常）、再怀疑模块注册（正常）、
最后直接 `node -e` 检查 `p.coupon` 是否存在 —— 一步定位。
**教训：改 schema 后必须 `prisma generate`，且排查「undefined of undefined」类错误时，
先验证 Prisma Client 是否有该模型，别急着查 Nest 的注入链。**

**② `prisma db push` 需要停服**
`The column User.inviteCode does not exist` —— schema 里有字段但表里没有。
push 时若后端在跑会挂起（SIGTERM），须先 kill。

**③ 前端类型契约必须实测，不能看 DTO 类名推断**
我按 DTO 写 `bonuses: []` + `valid: boolean`，后端实际返回 **`bonusRules`** + **`enabled`**，
还有 `maxStreak`/`dailyCap`/`configured` 三个字段我完全漏了。
**用 curl 打一次接口，把真实返回贴出来再写类型。**

**④ 前后端元/分单位不一致**
我 UI 传 `value: 5`（元），后端当**分**用（跟 `thresholdCents` 直接比较）。
后端有校验「减免金额不得超过使用门槛」—— 传元会让这道防线失效。
统一口径：**表单内存元，提交时 ×100 转分，载入时 ÷100 转元**；折扣的万分比不换算。

**⑤ Playwright 里 `\`${UI}/x\` 被我的批量替换搞坏了**
反引号被换成单引号 → `` `${UI}/admin/coupons'); `` → 文件语法错误 → "No tests found"。
（同一个坑这轮踩了两次：之前 `userId` → `user.id` 也是批量替换闯的祸。）

**⑥ 测试依赖唯一字段导致不可重复运行**
券码全局唯一，固定码第二次跑就撞「券码已存在」。改用时间戳片段。
另外把"编辑无券码输入框"用例改为**用已有券**而非先建券 —— 前置条件不再依赖建券成功。

### 环境
- 19 个 E2E 产生的券（含 ¥0.05 的脏数据）已清理，当前 0 张。

## M9.5 定时任务（调度器可观测 + B-90 补齐）

用户指令「定时任务」。后端冒烟 **30/30**、前端 E2E **6/6** 全通。

### 发现的关键缺口

`OrderService.cancelExpired()` 与 `CreditService.expireLots()` **两个方法早就写好了，但从未接进调度器**——
`SchedulerService` 的构造函数只注入了 `BackupService` / `SettingsService` / `MarketingService`。
B-90 三项里只有「数据保留期清理」真正在跑。这是典型的"写了但没接线"缺口。

### 三个设计决策

**① 失败隔离：每个任务独立 try/catch**
早期版本用一个大 try 包住全部任务，结果**备份抛错 → 订单超时关闭被整个跳过**。
订单不关闭会直接影响用户看到的可用金额 —— 一个无关任务的故障不该连累它。

**② 手动触发只开放幂等任务**
- 可触发：订单超时关闭、积分到期回收 —— 都是「扫一批已到期的」，重复执行无副作用
- 不可触发：备份、保留期清理 —— 会写文件/删数据，被随意触发可能**覆盖可用备份**

**③ 状态放内存而非 DB**
这些是每秒都在变的运行时指标，落库会把「最近调度状态」和「需要长期留存的任务审计」混为一谈。
需要长期留痕的任务自己写表（如 `CleanupLog`）。

节流：订单关闭最短 5 分钟、积分回收 10 分钟（订单超时本身是 30 分钟粒度，再密没意义）。

### 踩到的坑

**① SchedulerService 漏了 `@Injectable()`（真 bug）**
现象：`Cannot read properties of undefined (reading 'cancelExpired')`，
但源码里构造函数、`design:paramtypes`、dist 产物**全都正常**。
最终 `node -e` 检查 `Reflect.getMetadata('design:paramtypes', SchedulerService)` → **undefined**。

> **类上没有 `@Injectable()` 时，Nest 无法解析构造函数参数，全部注入为 undefined。**
> 而 TypeScript **不会报错**（`isolatedModules` 下装饰器元信息丢失也不提示）。
> 排查注入问题时，第一步就该查这个元数据，而不是查模块 imports。

**② 又是 dist 不同步**（同一个坑第 N 次）
源码里 `AdminSchedulerController` 注册了但 `dist/admin/admin.module.js` 的 controllers 数组里没有 →
404。根因是并行改动重写了 `admin.module.ts` 的那段，我之前的 `pythonreplace` 匹配失效但没报错。
`rm -rf dist/admin && npm run build` 强制重建才暴露出来。

> **规律：源码改了之后一定要 `npm run build`，且「源码有、dist 没有」= 没重新编译。**

**③ 我用 Edit + python 替换叠加，插了两份 `TASK_LABELS`**
`SyntaxError: Identifier 'TASK_LABELS' has already been declared`。
TS 编译没报错（同名 const 在同一作用域被合并），但 Node 直接崩。
**教训：同一个文件上不要混用 Edit 和批量替换。**

**④ SQLite 写锁：测试脚本紧随调度任务读会撞锁**
`database is locked`。调度任务在事务里批量写，测试脚本紧接着读就撞上。
加 `readWithRetry()` 短退避重试 —— 这是测试侧应对 SQLite 单写者限制的正当做法，不是掩盖缺陷。

**⑤ 系统负载 40+ 导致启动要 80 秒**
我误以为是代码问题。逐个测 `require` 耗时定位：`class-validator` 15.9s、`app.module` 20.5s——
全是磁盘 I/O 慢，与代码无关。清理残留进程后负载降到 14。

> **排查"启动慢"先看 `uptime`**，不要直接改代码。

### 验证（scripts/smoke-scheduler.js，30 项）
状态接口 6 / 白名单 3 / 订单超时关闭 3 / 积分回收 5 / 回收留痕 3 / 幂等 1 / 状态上报 6 / 审计 1 / 越权 2
关键语义：超时订单转 cancelled、未超时不受影响、**批次记录保留不删**、重复执行不重复写流水。

## 会员体系（落地页订阅卡兑现）

用户指令「会员体系」。**先核实现状** —— 完全不存在，但 PRD 第 177 行留了明确的技术债：
「C 端落地页现有订阅卡声明的 5 类权益中，4 类无模型承载，需删除或补建能力」。
落地页 `LandingPage.tsx` 四档套餐都在承诺「专享快速通道 / 同时处理多个任务 / 加油包95折」，
**全部无模型承载** —— 这不是加功能，是补一个欠下的承诺。

问清口径后开工：**订阅制 + 四项权益全做**（多选了全部三项 + 仅订阅积分）。

### 核心设计：非会员完全不受影响

`MembershipService.resolve()` **永不抛错**，失败时返回 `DEFAULT_PERKS` 而非 null。
这样调用方无需写「如果没有会员怎么办」的分支，会员表异常也不会拖垮下单与生成链路。

> **会员是增值项，不能成为主链路的单点依赖。**

`DEFAULT_PERKS` 三项必须等于「什么都不给」，任何一项调高都是让免费用户拿到会员待遇。

### 三张表
`MembershipPlan`（套餐+perks JSON）/ `Membership`（订阅实例，**带 perksSnapshot**）/ `MembershipUsage`（优惠留痕）

**perks 存 JSON 而非拆表**：权益是可变的运营配置，拆表会让「加一种权益」变成改表+加关联+改查询。
代价是失去 DB 校验，故在 `parsePerks()` 里严格校验（宁可默认值，也不让脏数据参与比较）。

**权益快照**：下单时把 plan.perks 复制到 membership.perksSnapshot。
实测：把 pro 套餐改成并发 99 后，存量会员**仍是 5** —— **用户已付的钱要对得起当时承诺的权益**。

### 四项权益的落地顺序（错一个就是资损）

**① 并发上限 —— 校验必须在扣费之前**
放在 `createTask()` 开头。若先扣费再校验，用户会为一次根本没创建的生成付费。
计数口径含 `pending` —— 已排队未开始的也算占位，否则狂点提交可无限堆积，上限形同虚设。
实测：超限返回 400，积分余额 400 → 400 不变。

**② 加油包 95 折 —— 折扣在汇总后、快照前**
顺序错了会让订单快照记折前价，退款时按折前价退，平台自亏。
实测：¥9.9 → ¥9.41（941 分 = 95.1%）。
`applyDiscount` 钳制在 1~10000 —— 超过 10000 会算出负价。

**③ 订阅积分** —— 首期立即发，之后由调度器按 `nextCreditAt` +30 天发放。
发放用**条件更新**（`where: { nextCreditAt: m.nextCreditAt }`）保证并发下只发一次。

**④ 快速通道** —— 存进 `task.params.__memberFastChannel` 随参数落库，供异步阶段读取。
不改全局 route 配置：route 是按能力的运营决策，会员只应在该能力允许远程时优先远程，
不能把 `local` 强制改成 `remote`。

**⑤ 续期顺延**：从 `max(当前到期时间, 现在)` 起算 —— 提前续费不损失剩余天数。

### 修掉的三个真 bug

**① `GenerationTask` 用 `ownerId` 不是 `userId`**
`Unknown argument 'userId'. Did you mean 'ownerId'?` → 500 而非 400。
GenerationTask/Asset 都用 ownerId，Order/CreditLot 才用 userId。

**② `include` 里不能放标量**
把 `membershipPlanId: true` 写进 `orderInclude()` → `include statements only accept relation fields`。
标量默认就在结果里。

**③ 折扣块被插入两次（真 bug，会二次打折）**
我的 Edit + python 替换叠加，产生了两段连续的
`const quote = await membership.quoteOrder(...); totalCents = quote.finalCents;`
第二次的入参已经是折后价 → **会员被打 9 折后再打 9 折**。
TS 不报错，Node 启动时才 `SyntaxError: Identifier 'quote' has already been declared`。
> **同一个文件上不要混用 Edit 和批量替换。**（这个坑我今天已经踩了 3 次）

### 测试自己写错的两处

**① 改套餐后没 try/finally 还原**
测试中途崩溃 → 套餐永久停在实验值（并发 99）→ 后续每次测试都跟着错，
且症状离真因极远。改为 try/finally 保证还原。

**② ECONNRESET 导致整体失败**
系统负载 40+ 时偶发连接重置。加 `call()` 重试，**只重试连接层错误**，
HTTP 5xx 照常返回（那才是要暴露的问题）。

### 环境/并行改动
- `OrderService` 被并行改动重写，我注入的 `membership` 依赖被冲掉过一次 → `Cannot read properties of undefined (reading 'quoteOrder')`。用 Edit 精确加回。
- `OrdersModule` / `GenerateModule` 都漏了 `MembershipModule` 的 imports（import 语句加了但数组没加）。
- 服务现在绑 `127.0.0.1` 而非 `localhost`，测试脚本要用 `127.0.0.1`。
- 启动约需 150s（负载高）。
