## /free-creation 生图链路 P0 修复：「永久生成中」

### 现象
`http://localhost:5173/free-creation` 点「立即生成」后按钮永久停在「生成中…」，
结果栏不出图。后端任务其实已succeeded（curl 直调 `POST /api/v1/generate` + `GET /api/v1/tasks/:id` 正常出图）。

### 取证（先跑红）
Playwright + 本机已装chromium-1134（`~/Library/Caches/ms-playwright/chromium-1134/chrome-mac/...`，
`node_modules/.bin/playwright` 自带版本需 `npx playwright install`，直接用 executablePath 指到 1134 可跑）：

| 观测点 | 修复前 | 修复后 |
|---|---|---|
| `GET /api/v1/tasks/:id` 请求数 | **0**（只有 POST /generate） | 2 |
| 按钮终态 | 生成中… | 立即生成 |
| 结果图 | 无 | 1 张 |

因果验证：临时把 `main.tsx` 的 `React.StrictMode` 换成 `Fragment` → 轮询恢复（发 1 次），
证明根因在 StrictMode 与 `usePollAbort` 的交互，而非后端。（验证后已还原 main.tsx。）

### 根因
`frontend/src/hooks/usePollAbort.ts` 在 effect cleanup 里直接 `controller.abort()`。
React 18+ 开发模式会**同步重放**一次 effect（mount → cleanup → mount），
首轮「假卸载」把 controller 打死，而 `ref.current` 仍指向这个已 aborted 的 controller，
第二次挂载拿到的 `signal.aborted` 恒为 `true`。
`lib/poll.ts` 的 `waitForTask` 首行即 `if (signal?.aborted) return PENDING`（永不 resolve 的 promise），
于是：轮询一次都不发 + `submitting` 永不复位。

### 修法
`usePollAbort.ts` 单文件：cleanup 里改为 `setTimeout(..., 0)` **延迟一拍**再 abort，
effect 体首行 `clearTimeout` 撤销上一次排队 的 abort。
StrictMode 假卸载的 abort 被撤销；真卸载语义与修复前完全一致。

该 hook 被 7 处消费，一处修复全部受益：
free-creation / product-kit / product-detail / viral-clone / multi-image-fusion / product-sku / ToolShell 修图系。

## M6/M7/M8 交易域：积分账本 / 商品 / 订单 / 沙箱支付 / 退款

用户指令「支付能力」。**先问口径再动手** —— 交易链的表结构由两个决策决定，问清了才开工：
- 定价口径：**只做积分消耗制**（无次数包/订阅包）
- 支付范围：**沙箱支付接口**（真实通道需商户号，属 M15）

后端冒烟 **36/36** 全通。前端交易页未做（下批）。

### 七张表，遵循 PRD §5 四条不可动摇的约定

`Product` / `Order` / `OrderItem` / `Payment` / `Refund` / `CreditLot` / `CreditLedger`

**① 余额唯一由 CreditLot 汇总推导，不存冗余余额字段**
冗余余额必然与批次不一致 —— 任何一次扣减失败或并发竞争都会留下偏差，而对账时无从判断该信哪个。**冗余余额是负债，不是优化。**
`CreditLedger.balanceAfter` 只是流水展示用的快照，出现不一致时以批次为准（代码注释写明）。

**② FEFO 扣减 + 条件更新防并发超扣**
`remainingCredits >= n` 的 `updateMany` 而非「读后写」。先读后写会丢失更新：两个并发请求都读到 100，各扣 80，余额成 -60。
余额不足时**整个事务回滚，一分不扣**。
⚠ SQLite 对 NULL 的默认排序是**最前**，与「expireAt 为空视为最晚到期」相反，故显式写 `nulls: 'last'`。

**③ OrderItem 全字段快照**
实测：下单后把商品价格改成 99999 分、名字改成「改价后名称」，历史订单金额仍 990 分、快照名仍「入门积分包」。

**④ 订单状态机不可跳跃**
`pending → paid → refunded/partial_refunded`，`pending → cancelled`。`TRANSITIONS` 表显式声明允许的迁移，非法迁移抛 409。
`refunded` / `cancelled` 是终态。

### 幂等：两处独立保证

**下单幂等**：数据库唯一约束 `(userId, idempotencyKey)` + 冲突后查回。
先查后插有竞态（两个请求同时查不到），靠唯一约束兜底才可靠。

**回调幂等**：`payTransactionId` 唯一约束 + 订单已是 paid 直接返回。
实测：重复支付同一订单，余额 500 → 500 不变。

### 退款语义（B-43，最容易做错的一处）

**退的是"还没花掉的部分"。** 实测：发 500 积分，人工扣 250 后退款——
- 扣回 250（还剩的）
- **如实记录 250 无法追回**（已消耗的）

不能静默吞掉这部分，否则对账会以为系统凭空丢了 250 积分。

### 沙箱支付三场景
`success`（发积分）/ `failed`（订单保持 pending 可重试，流水留痕）/ `timeout`（订单转 cancelled）。
失败也留流水 —— "发起过但没成功"是对账必须可见的事实。

### 踩到的三个坑

**① sed 式批量替换改坏代码**
`python3` 里做 `s.replace("userId","user.id")` 这类无边界替换，把 `userId: user.id` 变成 `user.id:` 造成语法错误；又两次把 `tempDir`/`finally` 块插入多处。文件未被 git 跟踪，无法回滚。
**教训：改已有代码用 Edit 工具做精确替换，批量脚本只用于新建文件。**

**② DTO 字段名与调用方不一致**
`AdjustCreditDto` 用了 `amount`，测试传 `delta` → 被 `whitelist: true` 剥空 → 报 `amount must be an integer`（误导性错误，实际是字段缺失）。
统一为 **`delta`** —— delta 明确表达「有正负的变动量」，amount 会被误解为「金额」或「绝对值」，后者让扣减无法表达。

**③ 改完代码忘了重新 build**
`commerce.controller.ts` 编译产物在，但 `dist/admin/admin.module.js` 的 controllers 数组里没有它 → 路由 `Cannot POST`。因为 build 在改代码之前跑的。
**排查手法**：源码里有、dist 里没有 → 就是没重新编译。

- 券 `usedCount` **只在支付成功时 +1**（下单不计数）：否则反复下单不付款即可耗光限量券。用条件更新 `usedCount < totalCount` 防并发超发。
- 支付流水金额记 **paidCents 而非 totalCents**；退款上限同样以 paidCents 为基准 —— 否则 100 元订单用 30 元券可退 100 元（直接资损）。
- 邀请码生成后自邀请被拒（`inviterId !== inviteeId`）；已绑定不覆盖（否则先到者丢失奖励归属，对账无从归因）。
- 签到 streak 由记录集推导，不存冗余字段；今天未签**不算断签**（断签要到明天才成立，否则白天没来得及签就显示误报）。
- 邀请奖励发放用条件更新 `pending→granted` 幂等；支付成功后触发，失败仅 WARN **不回滚支付**。

### 踩坑：node-sqlite-adapter 错误码映射失效（真实缺陷，影响全站）
冒烟跑出「同用户同日唯一约束生效」FAIL。实测发现 node:sqlite 错误对象有两个码字段：
- `code` = `"ERR_SQLITE_ERROR"`（**所有 SQLite 错误都一样，无区分度**）
- `errcode` = `2067`（真实扩展码，主码 19 + 子码 8<<8）

原 `mapDriverError` 的 `switch (error.code)` 按字符串名匹配，**永远不命中**，全部落 default 变 P2039。后果：所有依赖 `e.code === 'P2002'` 的幂等分支失效 —— 签到并发双击会 500 而非幂等返回。

`marketing.service.ts` 的 `isUniqueViolation()` 双判 P2002 与 P2039 是第二层保险（adapter 映射若再回归仍能兜住）。

## /free-creation 接真实模型（优云智算 ModelVerse）

**用户指令**：`/free-creation` 要「正式能力，没有 mock」。先问清落地方式，用户选**接真实模型网关** +

### 关键发现：优云智算与既有网关不同构

`GatewayImageProvider` 实现的是 aigc 自研**异步任务制**（`POST /generation/tasks` + 轮询）。
优云智算是 **OpenAI 兼容同步接口** `POST /v1/images/generations`，一次请求阻塞到出图。
**路径不同、响应结构不同、无需轮询 —— 改 baseUrl 复用不了**，必须新写 provider。

新增 `gateway.provider` 配置项（`aigc` | `modelverse`，默认 `aigc`）显式声明协议，
由 `CapabilityRouterProvider` 择一。选错症状：404/400 → 回落本地 → 产出 Jimp 占位图。

### 实测契约（qwen-image-3.0，2026-10-20）

- 请求 `{ model, prompt, size, image?, images? }`，`size` 形如 `1024x1024`
- 响应 `{ created, data: [{ url }] }`，URL 指向阿里云 OSS，**7 天失效**
- 失败 `{ error: { message, code } }`

### 关键设计裁定

- **`localImpl` 存字符串方法名而非函数**：definitions 若 import MockImageProvider，
  而后者要读 definitions 分派 → 循环依赖。故只登记名字，运行时按名取方法，
  并加**句柄存在性校验**（`resolveLocalImpl`）。另经 `LOCAL_IMPL_METHODS` 表转换，
  避免 `toString`/`constructor` 等原型属性名误过校验。
- **校验器只对 image 模态要求 localImpl**：文本/视频没有「本地算法」概念，
  对它们提要求等于逼人造假实现（造模板文案会让用户误认是模型产出）。

- **`buildPrompt` 的 refCount 改为显式入参**：旧代码往 params 里塞 `__refCount`

### 关键裁定

- **协议是「形状」，厂商是「身份」**，二者分开。同一协议可被多家厂商复用
  (openai 协议 → 优云智算/硅基流动/OpenAI 官方)。
- **协议层不得依赖厂商层**；**统一能力层不得依赖厂商层或协议层**（必须是叶子）。
- **`Modality` 抽成独立叶子模块** `providers/modality.ts` —— 放协议层会让统一层
  被迫依赖协议层, 破坏分层前提。断言里对叶子模块单独放行。
- **派生视图的 key 必须与重构前逐字一致**：规则是「厂商首个模态用裸 key,
  其余用 `<厂商>-<模态>`」。⚠️ 首版我按「一律加后缀」实现, 断言立刻红 ——
  `siliconflow` 变成 `siliconflow-image`, 会让**存量 `gateway.image.vendor` 对不上**。
  这是兼容性硬约束, 不是风格选择。
- **文本模态不暴露 sizeStyle/maxRefImages/refStyle**：协议层声明它们只为让
  ProtocolSpec 结构一致, 透出后后台会给文生文显示「像素尺寸 1024x1024」这种
  不存在的选项。
- **modelverse 保留具名子类**（不直接用基座）：它是本项目唯一实测可用的图像通道,
  具名子类便于排障时一眼看出走哪条路, 行为与其它 OpenAI 兼容厂商完全一致。

   `sourceSQL / expandedSQL` 两列假数据。另：**空结果集会打印一列空 `Values`**，
   需自行判空后打印 `(无数据)`。
2. **`val()` 只认 `--only=x`**，而帮助文本里两种写法混用 → 传 `--only bogus` 时
   值被**静默回落成 `all`**，非法参数按"全清"执行。加了空格形态分支。
   **判据：带值参数的默认值必须是"拒绝执行"而非"最危险的那个"。**
3. **zsh 下 `$c` 不做分词**：`for c in "--only audit"; do node x.js $c` 会把整串
   作为**单个** argv 传入（`["--only audit"]`），两种解析都匹配不上 → 又是回落 `all`。
   顺带发现 `node -e "..." -- --only audit` 里 node 会吃掉 `--`。
   已在脚本里加整串形态检测并硬失败。
   **判据：zsh 里未加引号的变量不做 word splitting，写测试循环要用数组或数组下标。**

## 添加模型厂商：MiniMax 视频通道（文/图/视 缺口补齐）

用户裁定：**厂商 + 协议 + 存储层全打通**（涉及 Prisma 迁移与改 generate.service）。

### 取证（官方文档，非凭印象）

MiniMax 视频 v1 是**四段式**异步契约：
1. `POST {base}/v1/video_generation` → `{ task_id, base_resp }`
2. `GET  {base}/v1/query/video_generation?task_id=xxx`
   → `{ status: Preparing|Queueing|Processing|Success|Fail, file_id?, video_width?, video_height? }`
3. `GET  {base}/v1/files/retrieve?file_id=xxx` → `{ file: { download_url } }`
   ← **这一步是 MiniMax 特有**，Success 只给 file_id，不给地址
4. `GET  download_url` → 视频字节

⚠️ 状态枚举**首字母大写**（Success/Fail），与图像侧小写风格不同 → 协议层做大小写无关归一。
⚠️ 轮询用**query 参数**而非路径段。

### 落地

| 层 | 改动 |
| --- | --- |
| 协议层 | 新增 `VideoProtocolSpec` + `VIDEO_PROTOCOL_SPECS`（**与图像的 ProtocolSpec 分开**） |
| 厂商层 | minimax 加 video 通道（协议 `minimax-video`）→ 派生视图 `minimax-video` |
| 能力层 | 新增 `image_to_video` 能力（**无 localImpl** —— 视频没有本地算法） |
| 统一层 | `minimax-video.provider.ts` 四段式实现 + `video-format.ts` 魔数判定 |
| 路由层 | `VideoCapabilityRouter`（**无本地兜底**）+ `VIDEO_PROVIDER` token |
| 存储层 | `Asset.durationMs` + `ModelCallLog.modality` + generate.service 按模态分流 |
| 前端 | `ResultMedia` 组件（video 用 `<video>`）+ 4 处渲染点 + 类型 |

### 关键裁定

- **视频协议形状独立于图像协议形状**：视频四段式 vs 图像一次 POST，
  硬塞进同一 interface 会逼出 `if (isVideo)` 分支蔓延。
- **视频能力无 localImpl、视频路由无本地兜底**：本地不存在"生成视频"这回事；
  编占位素材会让用户误以为模型产出。
- **视频不走了 Jimp.read**：Jimp 只解图片，喂 mp4 抛 "Unsupported MIME type" → 任务永远失败。
- **存储扩展名按 mime 推导**：原先"png 用 png 其余 jpg"会把视频存成 .jpg，
  存储后端按扩展名推断 Content-Type 发 image/jpeg → 浏览器按图片解码视频 → 播放失败。
- **产出模态按 mime 推导而非查能力注册表**：产出形态是文件的真实形态，
  不该由"当初打算产出什么"决定（能力改版后历史产出仍是旧形态）。
- **文本通道补了埋点**：此前文本**完全不写** ModelCallLog →
  "文本调用在记录页不可见"，无法区分"没调用过"与"调用了但没记录"。

### 踩坑

1. **漂移检测器漏了视频目录**：`collectViewDriftIssues` 只查 `PROTOCOL_SPECS`，
   把合法的 `minimax-video` 预设误判为"协议不存在"—— **假红灯**。
   修法：同时查 `VIDEO_PROTOCOL_SPECS`。
2. **bootstrap 断言一刀切要求 localImpl**：漏了"只有 image 模态才要求"这条
   （与能力层校验器同源的规则，断言里没跟上）。已按模态分流。
3. **基线断言再次需要"新增须登记"**：能力 15→16、预设 9→11，
   按已确立的规矩改为「基线逐字未变 + 新增项显式登记」。

### 最重要的结论：三类「模型设置」取向相反，不能混抄

| 类 | 代表 | 用户 | 取向 |
|---|---|---|---|
| A 多厂商网关 | New API / One API | 运维，设一次长期不改 | 状态与健康度优先 |

## 按竞品调研建议实施三项改进（19:07）

### 实施前先审计 → 查出一个更严重的真缺陷

调研报告里第 3 点是「通道测试须匹配模态」（Teable 做法）。
实施时发现**探测路径按模态硬编码**这个更严重的问题：

`probePath(modality)` 让 image 恒打 `/generation/tasks` ——
那是 **aigc 自研网关**的路径。而 5 个图像协议的真实端点各不相同：
```
aigc → /generation/tasks        openai → /v1/images/generations
volcengine → /images/generations  minimax → /v1/image_generation
```
配了 `openai` 协议时探测打的是优云智算/硅基流动**根本不存在**的路径，
拿到 404，而探测把 4xx 当「网络可达」→ **测试显示通过，生成必然 404**。

这正是调研报告里说的「探测通过 ≠ 实际能调通」，
且与本项目最忌讳的「静默不实」完全一致。

**修法（架构一致性）**：探测路径由**协议层**声明
（`ProtocolSpec.probePath` / `VideoProtocolSpec.probePath`，缺省取 endpoint 的路径），
与生成端点同源 —— 改一处两处都对，不再有第二个真相源。

### 三项改进

| # | 改进 | 落点 |
|---|---|---|
| ① | **批量测试全部通道** | `POST /admin/model-config/test-all` → `testAllConnections()`（并发，`Promise.allSettled`）|
| ② | **高级配置默认折叠** | `CollapsiblePanel` 组件；「超时与轮询」9 项默认折叠，状态存 localStorage |
| ③ | **测试区分「可达」与「可用」** | 探测后拉模型列表校验模型名；状态码分档 |

### ③ 的关键设计（状态码分档）

改造前**任何 4xx 都算 ok:true「网络可达」**。分档后：

| 状态码 | 判定 | 依据 |
|---|---|---|
| 2xx | 通过 | 端点存在且接受该方法 |
| 405/501 | **端点确实存在** | 只是不接受 OPTIONS —— 强正向信号 |
| 401/403 | **失败**：令牌被拒 | 端点存在但令牌无效 → 生成必然失败 |
| 404 | 换 GET 再探一次 | 404+404=端点不存在→失败；404+405=端点存在→通过 |
| 5xx | 失败 | 网关自身故障 |

**为什么要换 GET 再探**：404 有歧义（服务器不处理 OPTIONS / 路径真不存在），
后果完全相反。GET 打 POST-only 的生成端点：405=端点存在，404=真不存在。

**模型名校验**：拉 `{base}/v1/models`（或 `{base}/models`）检查模型名在不在。
- 在 → 「模型可用」
- 不在 → **报失败**并给出可用模型样例（只说"不在列表里"运营还是不知道填什么）
- 拉不到（厂商不提供）→ 「未验模型名」，**既不报失败也不谎称可用**

⚠️ 路径**不统一**（取证）：DeepSeek 是 `{base}/models`（无 /v1），
OpenAI/硅基流动是 `{base}/v1/models`。同一协议服务 5 家厂商，
故声明为**候选列表**依次尝试 —— 猜一个统一路径必然对某家不对（猜错=静默漏检）。

### 关键裁定

- **探测端点属协议层事实**，不属「按模态」的通用规则 —— 放协议层才与生成同源。
- **模型列表端点声明为候选列表**而非单路径：协议层本不该知道有 DeepSeek 这家厂商。
- **模型列表拉不到 ≠ 验证失败**：三态（可用/不可用/无法验证）必须分开。
- **批量测试用 allSettled 而非 all**：某模态失败不该让其它模态结果也拿不到。
