## 支付模块架构审计（backend/src/payments + orders）

完成一次支付域全量代码审计（约 6k 行），产出分层架构说明与缺陷清单。核心结构：适配器契约 + PaymentCoreModule 叶子模块 + PaymentOrderService 编排 + OrderService 唯一入账 + PaymentNotification 收件箱 + PaymentReconciliation 对账 + PaymentWorker 定时。

已确认缺陷（按严重度）：
- P0 会员订阅订单不生成 OrderItem，而 `payment-query.ts:189` 后台支付订单查询强制 `items: { some: {} }`，导致会员单在后台支付列表/导出/查单/关单全不可见；GMV（overview.service.ts:119）却包含，口径不一致。admin 目录无任何 membershipPlanId 入口。
- P0 退款「渠道成功→本地记账」三步（refund.update → transition → order.refundedCents）无事务/补偿，崩溃后 refundedCents 不增长，可重复退款（可退额度只按 refundedCents 算）。
- P0 收件箱同步处理不占锁：ingest 直接 processNotification，仅 retry() claim 成 processing，worker 15s 扫描可并发处理同一事件。
- P0 `lastError` 一字段两用：查单失败写入 → paymentStatusOf 判 create_failed，正常 pending 单显示「发起失败」红色。
- P1 对账 compareOne 的 configId 只判空、实际用 configs.latest()，与配置版本固定原则脱耦。
- P1 close() 接受 not_found 视为已关，与 types.ts 注释、query() 的 not_found 判定三处口径冲突。
- P1 OrderService.cancelByUser 死代码，路由实由 OrderCancelController → PaymentOrderService.close 承接。
- P1 worker 内存 running 锁 + lastAutoReconcileDate，多实例会重复自动对账。
- P1 CSV 千分位金额 parseFloat NaN 静默丢行。

结论：架构本身健壮（版本化凭据、唯一入账、渠道多尝试模型、差异落对账都对），问题集中在「会员单口径」「退款记账原子性」「展示状态语义」三处。未修改任何代码，等待用户裁定优先级。
