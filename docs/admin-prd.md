## 1. 背景与目标

### 1.1 现状

货觉AI 已具备完整商业闭环：16 项能力（15 项图像 + 1 项视频）全部由真实模型产出，交易域覆盖商品 / 订单 / 支付 / 退款 / 积分 / 会员，后台管理端 29 页、54 个权限点。数据模型 43 张表，数据库为 SQLite 单文件，由后台定时备份与保留期清理托底。

### 1.2 目标定义

系统目标是**正式对外收费运营**，承担真实用户的资金往来、个人信息处理与内容生成责任。

这一定位带来两项与演示环境本质不同的要求：

| 要求 | 含义 |
|---|---|
| 数据可托底 | 承载真实交易与个人信息，数据丢失不可接受，须有备份与恢复能力 |
| 服务有 SLA | 用户付费后即形成服务关系，任务失败、支付异常、投诉举报须有时限内响应 |

### 1.3 后台目标

| 目标 | 衡量 |
|---|---|
| 可运营 | 能处理用户举报、任务故障、订单异常，且有 SLA 约束 |
| 可收钱 | 能配置商品、下单、核销、退款、对账 |
| 可合规 | 标识注入、内容处置、审计留痕可执行可举证 |
| 可配置 | 能力上下架、消耗价、通道、站点参数不发版调整 |
| 可控制 | 越权不可达，高危动作二次确认且留痕 |
| **可托底** | 数据可备份可恢复，服务故障可告警可追溯 |

### 1.4 后台不负责

生成任务的实际执行（由 C 端与后端服务完成）· 内容创作 · 模型通道的算法实现 · 用户侧的前端体验

## 2. 使用者与权限

### 2.1 角色

| 角色 | code | 定位 | 人数预期 |
|---|---|---|---|
| 平台管理员 | `admin` | 全部权限，含系统配置与角色管理 | 1 |
| 运营 | `operator` | 用户、素材、任务、合规只读 | 1-3 |
| 财务 | `finance` | 商品、订单、支付、积分。用户数据只读 | 1 |

**三分角色的理由**：财务可改钱，运营可删数据。权限合并后无法追责，审计日志也失去意义。

| 任务监控 | ✎ | ◐ | — |
| 合规中心 | ✎ | ◐ | — |

| 积分账本 | ✎ | — | ✎ |

### 2.3 强制规则

| 规则 | 实现 |
|---|---|
| 权限粒度 | `<模块>.<动作>` 字符串，如 `user.write` `order.refund` `credit.adjust` |
| 兜底默认拒 | 权限未命中即 403 |
| 每次查库 | 权限校验实时读库，不信 token 内的 role（JWT TTL 7 天，只信 token 会导致降权后旧凭证仍可用） |
| 禁止提权 | 只有 `admin` 能授予 `admin`（否则 403 `40301`）；不能变更自己的角色（400 `40001`） |
| 最后一个 admin | 禁用与降级前统计启用中的 admin 数，`≤1` 返回 409 `40901` |
| 高危动作 | `order.refund` `user.delete` `user.reset_password` `credit.adjust` `setting.write` `role.write` `channel.route` `capability.write` 二次确认 + 填原因 + 写审计 |
| 审计不可删 | 审计记录只读，无删除接口 |

### 2.4 管理员账号

普通用户与后台管理员是两套账号：普通账号由 `SEED_USER_EMAIL` 决定且永不给 admin 角色；后台管理员用 `npm run seed:admin` 初始化。development / test 统一使用 `admin@admin.com / 123456789`；production 默认生成 20 位随机密码，仅在本次运行打印一次，不写库不落盘，重复执行不重置已有密码。前端产物中不硬编码任何凭据，登录页也不提供「填充演示账号」。

## 4. 界面需求

### 4.1 外壳

| 项 | 要求 |
|---|---|
| 布局 | `AdminLayout`：侧栏 240px 固定 +顶栏 56px + 内容区 |
| 独立性 | 不复用 C 端的 `AppLayout` / `SideRail` / `PromoBar`（均为 C 端语义） |

### 4.2 页面规范

| 类型 | 规范 |
|---|---|
| 列表页 | 页头（标题 + 主操作）→ 筛选条 → 表格 → 分页。统一 `rowKey="id"`、`size="small"`、带分页尺寸切换 |
| 详情 | 一律抽屉（宽 720px），不跳独立路由 |

| 空态 | 明确空态说明，不留空白 |
| 加载 | 表格 `loading`；骨架屏仅首屏 |
| 数字 | 金额统一两位小数（内部存分）；积分整数千分位 |
| 时间 | 统一 `YYYY-MM-DD HH:mm` |

### 4.3 样式约束

只使用 `global.css` 已定义的语义化 token，**禁止硬编码色值**。新增后台样式统一前缀 `adm-`。

### 4.4 响应式

后台最小宽度 1280px，窄于此横向滚动。不做移动端适配（运营使用桌面）。

## 5. 数据需求

### 5.1 现有表（4）

`User` · `Project` · `Asset` · `GenerationTask`

### 5.2 新增表（18）

| 域 | 表 |
|---|---|
| 权限 | `AdminRole` |
| 审计与配置 | `AdminAuditLog` · `SystemSetting` |
| 交易 | `Product` · `Order` · `OrderItem` |
| 资产 | `CreditLot` · `CreditLedger` |
| 合规 | `AigcStamp` · `ComplianceLog` · `ContentReview` |
| 数据安全 | `BackupRecord` |
| 消息 | `Notification` · `Announcement` · `MessageTemplate` |
| 服务 | `Ticket` · `TicketMessage` |

### 5.3 字段扩列

| 模型 | 新增字段 | 用途 |
|---|---|---|
| `User` | `role`（user/admin/operator/finance） | 后台权限判定 |
| `User` | `status`（active/disabled/deleted） | 账号状态 |
| `User` | `lastLoginAt` | 用户列表展示 |
| `Asset` | `status`（visible/hidden） | 素材下架 |
| `GenerationTask` | `creditCost` | 扣费快照与后台展示 |
| `CapabilityDef` | `creditCost` | 消耗价代码兜底默认值 |

### 5.4 核心规则

| 规则 | 说明 |
|---|---|
| 余额推导 | 可用余额 = Σ `CreditLot.remainingCredits`（未过期）。不存冗余余额字段 |
| 扣减顺序 | 按 `expireAt` 升序逐批扣，为空视为最晚 |
| 金额单位 | 整数，单位分。不使用浮点 |
| 订单快照 | `OrderItem` 全字段快照，商品改价不影响历史订单 |
| 幂等下单 | 按 `idempotencyKey` 去重，重复请求返回同一订单 |
| 幂等回调 | 按 `payTransactionId` 去重，已支付订单重复回调不重复发积分 |
| 并发扣减 | 条件更新（`remaining >= cost`）配合 SERIALIZABLE 事务，不使用行锁 |
| 订单留存 | 订单与交易信息保存不少于 3 年（《电子商务法》），不参与数据清理 |
| 备份可恢复 | 每份备份须有恢复验证记录，无验证记录的备份视为无效 |
| 审计 | 只追加，不可修改与删除 |

## 7. 非功能需求

| 类别 | 要求 |
|---|---|
| 越权防护 | 非管理员访问返回 403；越权用例纳入端到端测试 |
| 审计完整性 | 所有写操作留痕，含操作人、时间、对象、原因、IP |
| 高危防护 | 退款、删数据、调价、积分增减需二次确认 |
| 记账正确 | 余额唯一由批次推导，禁止直接改余额 |
| 一致性 | 订单状态机不可跳跃；支付回调幂等 |
| 数据留存 | 订单与交易信息保存不少于 3 年（《电子商务法》） |
| 可追溯 | 关键操作可按 userId / orderId 串联完整链路 |
