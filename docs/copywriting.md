# 用户可见文案规范

全站用户可见文案的单一标准：C 端页面与后台管理端共用同一套写作基准、禁止项与自检清单。文案改动与页面实现同批交付，不做事后补写。

## 1. 任务边界

优化所有**面向人**的文案：页面标题与副标题、按钮与链接、菜单项、表单标签与占位符、校验提示、帮助说明、能力介绍、套餐与积分说明、空状态、加载状态、失败状态、Toast、确认弹窗、错误提示、站内消息、邮件与短信模板，以及后台的字段说明、操作提示和危险动作确认。

不包含：日志、代码注释、变量名、仅开发者可见的调试信息。

分两档执行：

- **C 端**：一律用业务语言，不出现任何实现概念。
- **后台**：允许「渠道 / 模型 / 绑定 / 能力」等业务术语（后台就是在配置这些），但禁止接口路径、字段名、错误码、状态枚举、协议标识。

## 2. 写作基准

1. **运营视角**：说「用户要完成什么」，不说「系统是怎么实现的」。
2. **专业**：术语准确、口径统一、不夸大、不卖萌。
3. **指引**：每条文案都能回答「现在做什么 / 接下来会发生什么 / 失败后怎么办」。
4. **简洁**：一句话只承载一件事，删掉不提供信息的句子。

## 3. 禁止项（按特征识别，不靠感觉）

| 类型 | 识别特征 | 反例 |
| --- | --- | --- |
| 技术性文案 | 错误码、接口名、字段名、状态枚举、协议/渠道标识、HTTP 与数据库概念 | `42204 无可用线路`、`channel_unavailable`、`modelKey` |
| 开发类文案 | TODO、占位符、Lorem、「开发中」、「敬请期待」、注释式说明 | `该功能正在开发中`、`测试数据` |
| 无信息量文案 | 复述界面、空话套话、「操作成功」、重复标题的副标题 | `点击按钮即可生成`、`致力于为您提供优质服务` |
| 非自然语言 | 机器拼接、未解释的缩写、生硬直译、符号堆砌、中英混排 | `{capability}不可用`、`请检查您的网络连接状态` |
| 假设性文案 | 「可能 / 也许 / 大概 / 预计」代替确定行为；承诺无法保证的时间、成功率、结果 | `通常 3 秒出图`、`如果失败请重试`（无原因无动作） |

补充两条硬规则：

- 错误码只留在日志里，界面必须转成「发生了什么 + 是否扣费 + 下一步」。
- 不确定的结果不许用模糊词糊过去，必须给明确状态和人工入口（对应「结果不明」一类场景）。

## 4. 分场景写法

| 场景 | 必含要素 | 示例 |
| --- | --- | --- |
| 按钮 | 动词 + 对象，2–6 字 | `生成图片`、`保存草稿` |
| 空状态 | 为什么空 + 一个动作 | `还没有作品。上传一张商品图，开始第一次创作。` |
| 错误提示 | 发生了什么 + 是否扣费/可否恢复 + 下一步 | `生成失败，积分已退回。请调整图片后重试。` |
| 确认弹窗 | 动作 + 后果 + 是否可撤销 | `删除后素材无法恢复，已生成的作品不受影响。` |
| 成功提示 | 结果 + 下一步 | `已保存到素材库。继续生成或前往查看。` |
| 帮助说明 | 一句结论 + 限制条件 | `每次生成消耗 10 积分，失败自动退回。` |
| 加载状态 | 正在做什么 + 可否离开 | `正在生成，可离开页面，稍后在作品中查看。` |
| 能力不可用 | 状态 + 是否扣费 + 替代路径 | `该功能暂未开放，本次不会扣除积分。` |

## 5. 语言规范

- **人称**：C 端统一用「你」；后台用职业表述，全站不混用「你 / 您」。
- **语态**：主动、肯定。能说「积分已退回」，不说「将进行退回处理」。
- **句长**：单句 ≤ 25 字，单条说明 ≤ 2 句。
- **数字**：阿拉伯数字 + 单位，写具体值（`3 张`、`10 积分`），不写「若干 / 多张」。
- **标点**：中文全角，省略号用「…」，不用连续感叹号，不用 emoji 承载语义。
- **术语**：能力、任务、作品、素材、积分、套餐等，同一概念全站只用一个词，以产品术语为准。
- **承诺**：只描述系统确定会做的事；给不出保证的，写清条件和处理方式。

## 6. 执行与交付

1. 先盘点：按「页面 / 组件 / 文案来源」列出所有用户可见文案，明确 C 端与后台各自范围。
2. 逐条产出对照表：`位置 | 原文 | 问题类型 | 优化后 | 一句话理由`。
3. 只改文案，不改交互与逻辑；需要补充说明时优先复用现有提示位，不新增弹窗。
4. 错误码、状态、字段到文案的映射集中维护，禁止在页面里散落硬编码字符串。
5. 后台危险动作（退款、扣积分、删除、调价）文案必须写清后果与能否撤销。

## 7. 交付前自检

- [ ] 删掉任意一句，用户是否会缺少必要信息？不会则删。
- [ ] 是否出现用户不需要知道的实现细节？
- [ ] 每条文案是否只有一个明确的下一步？
- [ ] 是否承诺了系统无法保证的时间、成功率或结果？
- [ ] 空状态和失败状态是否都给了原因与动作？
- [ ] 术语、数字格式、标点是否与全站一致？
- [ ] 能否自然朗读，且不啰嗦？
- [ ] 是否残留 TODO、占位符、「开发中」、「敬请期待」？
