# 错误文案映射规范

错误码的**语义**在 [`api-contract.md`](api-contract.md) §2 与各 service 就近定义；用户可见文案的**写法**在 [`copywriting.md`](copywriting.md)。本文件规定两者的接缝：哪个码由哪一层出文案、按什么结构写、未知码怎么兜底、新增时改哪里。

## 1. 职责分层

| 层 | 产出 | 事实源 | 约束 |
| --- | --- | --- | --- |
| 后端业务异常 | `AppError(code, message, httpStatus)` | 各 service | `message` 是默认文案，必须是自然语言 |
| 前端请求层 | `ApiError(message, status, code, requestId, retryAfter)` | `frontend/src/lib/api.ts` | 后端 `message` 原样透出；5xx 追加请求号；被动 401 覆盖为「请先登录」 |
| 前端按码覆盖 | 可执行的下一步提示 | 使用该码的功能目录内 | 只按 `code` 判断，且只在该功能内生效 |
| 任务失败码 | `task.errorCode`（字符串） | C 端 `constants.ts` 的 `TASK_ERROR_TEXT`；后台 `admin-error-codes.ts` 的 `TASK_ERROR_LABELS` | 两端分别维护，不共用同一句话 |

四条规则：

1. **后端 `message` 是主文案**。前端覆盖只用于两种情形：需要给出「下一步去哪做」，或后端文案含内部概念。
2. **不按 message 文本匹配**。文案会改，只按 `code` / `status` 判断。
3. **码可能跨域复用**（见 §5）。覆盖表必须放在使用它的功能内，不做全局「码 → 文案」大字典，否则改一处会影响无关页面。
4. **未知码不隐藏**。C 端给兜底话术；后台同时保留原始码与兜底说明；日志始终记录原始码。

每条错误文案都必须回答三件事：**发生了什么 / 钱和产出怎么样了 / 下一步做什么**。少任何一项都不合格。

## 2. 文案结构

| 处置方 | 结构 | 示例 |
| --- | --- | --- |
| 用户可处置 | 原因 + 一个动作 | `积分不足，请充值后再试`、`操作过于频繁，请 30 秒后再试` |
| 运营可处置 | 当前状态 + 已采取的动作 + 等待/联系入口 | `生成结果暂不明确，积分已冻结，等待人工核对` |
| 系统异常 | 未完成 + 是否扣费 + 稍后重试或联系客服 + 请求号 | `生成失败，积分已退回。请稍后再试（请求号 xxx）` |
| 结果不明 | 不承诺成功也不承诺失败 + 冻结说明 + 人工核对 | `结果暂不明确，积分已冻结，等待人工核对` |

硬性要求：

- 「请稍后再试」不能单独出现，必须同时说明是否扣费、产出是否已交付。
- 结果不明（`42206`）禁止出现「重试」诱导；重试可能造成二次计费。
- 后端 `message` 禁止拼状态枚举、字段名、渠道或协议标识、上游原始报错、堆栈与文件路径。确需保留的诊断信息只进日志。
- 后台文案可以比 C 端多给排查方向，但同样不出现上述内部标识。

## 3. 码段约定

| 码段 | 语义 | HTTP | 备注 |
| --- | --- | --- | --- |
| `40000`–`40009` | 参数与前置条件 | 400 / 409 | `40001` 是通用校验，出现频率最高 |
| `40100`–`40103` | 登录与凭证 | 401 / 400 | 登录接口的 401 原样透出后端文案，不覆盖为「请先登录」 |
| `40200`–`40201` | 余额不足 | 402 | 前端统一给「去充值」入口 |
| `40300`–`40304` | 权限、账号状态、临时密码 | 403 | 越权在工单域刻意用 404 |
| `40400`–`40402` | 资源不存在 | 404 | |
| `40900`–`40909` | 状态冲突 | 409 | 跨域复用最多的一段，见 §5 |
| `41000` | 资源已过期 | 410 | 目前用于移动上传二维码 |
| `42201`–`42206` | 生成任务失败 | 任务内 | 唯一一组要求 C 端与后台分别维护文案的码 |
| `42901` | 限流 | 429 | 必须带 `Retry-After` |
| `50000`–`50002` | 服务端异常 | 500 | |
| `50201` | 上游文本能力失败 | 502 | 提示词工具使用 |
| `50301`–`50303` | 依赖未就绪 | 503 / 502 | 支付通道、渠道退款、模型代理 |

新增码按 HTTP 语义选段；同一功能内不得复用已有含义。`422xx` 为生成任务保留，其他模块不得占用。

## 4. 生成任务码表（现行）

C 端文案在 `frontend/src/lib/constants.ts`，通过 `taskErrorText()` 使用；后台文案在 `frontend/src/lib/admin-error-codes.ts`，通过 `taskErrorLabel()` 使用。

| 码 | 含义 | C 端文案 | 后台文案 |
| --- | --- | --- | --- |
| `42201` | 有线路但全部失败 | 生成失败，积分已退回 | 生成过程异常 |
| `42202` | 中断回收失败 | 任务中断，产出未完成（积分已退回） | 任务中断，产出未完成（已退款） |
| `42203` | AIGC 角标写入失败 | AI 标识写入失败，本次未交付图片（积分已退回） | AI 标识写入失败，未交付（已退款） |
| `42204` | 无可用线路 | 暂无可用模型通道，本次未生成图片（积分已退回） | 无可用模型通道 |
| `42205` | 无支持遮罩的线路 | 当前模型通道不支持遮罩重绘，本次未生成图片（积分已退回） | 无支持遮罩的线路（已退款） |
| `42206` | 结果不明，待人工核对 | 生成结果暂不明确，积分已冻结，等待人工核对 | 结果不明，待人工核对（未自动退款） |
| `CANCELLED` | 用户或系统取消 | 任务已取消，本次未产出图片；退款以账单处理结果为准 | — |
| `POLL_TIMEOUT` | 前端轮询超时 | 等待超时：任务可能仍在后台生成，请稍后到「我的作品」查看（若失败会自动退回积分） | — |
| `cancelled_by_admin` | 后台终止 | — | 后台终止 |
| `unknown` | 后端未落码 | 未知错误 | 未记录错误码 |

已知差异：C 端未登记码使用兜底话术「任务未完成，请稍后在「我的作品」查看；若积分有异常，请联系客服」，不再直接显示数字码。

## 5. 码复用清单（覆盖时必查）

同一个码在不同功能里含义不同，前端覆盖必须限定在功能内：

| 码 | 含义 A | 含义 B |
| --- | --- | --- |
| `40002` | 邮箱/短信验证码缺失（`auth`） | 积分不足（`credits`，见 api-contract） |
| `40900` | 排序列表已被他人修改（渠道排序） | 幂等键已用于不同请求（任务准入） |
| `40908` | 退款仍在渠道处理中（订单） | 二维码状态已变化（扫码登录） |
| `40909` | 插件仍被渠道模型引用（插件卸载） | 退款单与异常单不一致（支付异常核销） |

新增覆盖前先在本表确认该码是否已有其他含义；有则把映射写在使用处，不写入共享表。

## 6. 新增与修改流程

1. 按 §3 选码，在 service 里抛 `AppError(code, message, status)`；`message` 按 §2 的结构写。
2. 判断是否需要前端覆盖：只有当用户需要「下一步去哪做」，或后端文案无法避免内部概念时才加。
3. 覆盖映射放在功能目录内（参考 `pages/admin/orders/refundRuleHint.ts`），并为「命中 / 未命中」各写一条测试。
4. 生成任务码需同时更新 `constants.ts`（C 端）与 `admin-error-codes.ts`（后台），两端文案不要求相同。
5. 跨模块使用的码同步更新 [`api-contract.md`](api-contract.md) §2；本文件 §4 / §5 同步更新。
6. 修改文案后跑 `npm --prefix frontend test`，确认引用该码的页面与用例没有断言旧文案。

## 7. 交付前自检

- [ ] 文案是否同时回答了「发生了什么 / 钱和产出 / 下一步」？
- [ ] 是否把状态枚举、字段名、渠道或协议标识、上游报错、文件路径写进了 `message`？
- [ ] 是否按 `code` 而不是 message 文本做判断？
- [ ] 覆盖映射是否放在功能目录内，而不是全局字典？
- [ ] 未知码是否有兜底，且原始码仍可在后台与日志中查到？
- [ ] 结果不明类文案是否避免诱导重试？
- [ ] C 端与后台是否使用了各自视角的文案？

## 8. 已知缺口

- **码复用**：`40002` / `40900` / `40908` / `40909` 仍在不同域承担不同含义（见 §5），新增复用目前只能靠人工检查。
- **无常量表**：错误码仍以数字字面量散落在各 service，没有可枚举的常量表。
- **技术术语过滤不通用**：只有提示词工具有 `promptToolMessages.ts` 的过滤逻辑，通用请求层没有。
- **后台配置类文案带标识**：如「未知支付渠道: xxx」「状态筛选值非法: xxx」会带内部标识，属于后台可接受范围，但不得复用到 C 端。
