# 状态与反馈规范

用户在任何时刻都应该能判断三件事：**现在是什么状态、要不要等、下一步做什么**。本文件统一加载、空、失败、进行中、成功与结果不明这六类反馈的判定顺序、组件取用与文案结构；文案写法遵循 [`copywriting.md`](copywriting.md)，错误码文案遵循 [`error-copy.md`](error-copy.md)。

## 1. 判定顺序

一个区域同一时刻只能处于一种状态，按以下顺序判定，先命中先显示：

| 顺序 | 状态 | 判定 | 禁止 |
| --- | --- | --- | --- |
| 1 | 不可用 | 能力已下线、无可用线路、无权限 | 渲染成空态或失败态 |
| 2 | 加载中 | 首次请求未返回，且没有旧数据 | 清空版面、只显示纯文本 |
| 3 | 有数据 | 请求成功且数据非空 | — |
| 4 | 空 | 请求成功且数据为空 | 与失败态混用 |
| 5 | 失败 | 首次请求失败且没有旧数据 | 显示「暂无数据」 |
| 6 | 陈旧 | 刷新失败但保留了上一次数据 | 静默当作成功 |

**空、失败、不可用是三件事**：空是「这里本来就没有」，失败是「没取到」，不可用是「当前不能做」。把失败渲染成空态属于谎报状态，用户会以为数据丢了或自己没创建过。

## 2. 生成任务状态

后端任务状态只有 `queued / running / succeeded / failed / cancelled`；账单另有 `reserved / settled / uncertain`，两者不是同一状态机。

| 后端状态 | C 端展示 | 后台展示 | 组件 / 文案 |
| --- | --- | --- | --- |
| `queued` | 「生成中…」（与 `running` 合并） | 排队中 | C 端不区分排队，避免用户误以为没提交 |
| `running` | 「生成中…」 | 进行中 | 骨架占位 + 明确文案 |
| `succeeded` | 结果图 / 结果列表 | 已完成 | — |
| `failed` | `taskErrorText(errorCode)` | 失败 + `taskErrorLabel` | 必须说明钱与产出 |
| `cancelled` | 统一按 `CANCELLED` 文案 | 已取消 / 后台终止 | — |
| 账单 `uncertain` | 对应 `42206` 文案 | 结果不明 | 不切线、不退款，等人工核对 |

规则：

- **提交后立即进入生成中**，不得退回「还没提交」的空态。结果栏先清空旧结果时，必须同时渲染生成中占位（`ToolGeneratingState` 或等价骨架），不能只剩空态插画。
- **轮询期间的网络抖动不报错**：单次请求失败继续轮询，达到上限才按 `POLL_TIMEOUT` 提示「任务可能仍在后台生成，稍后到我的作品查看」。
- **结果不明不给重试入口**。`42206` 可能已在上游产出并计费，重试会造成二次扣费；只给查看与联系客服。
- 后台区分 `queued` 与 `running`，C 端不区分；同一状态在两端不要求同一文案，但语义必须一致。

## 3. 加载

### 3.1 首屏

| 端 | 做法 |
| --- | --- |
| C 端 | `StateSkeleton`（`card` / `row` / `panel` / `block`），占住最终布局 |
| 后台 | `PageSkeleton`：**页头标题与说明照常渲染真实文字**，只把数据区换成 `SkeletonPanel` / `SkeletonStats` / `SkeletonCards` |

骨架占的是位置，不是把版面清空。首屏不能只剩几根灰条，也不能只显示「加载中…」纯文本。

### 3.2 块内与操作

- 面板、弹窗、抽屉内加载：`SkeletonBody`（后台）或 `StateLoading`（C 端，必须带文案）。
- 按钮提交：按钮内置 `Spin` + 文案（如「生成中…」），同时 `disabled` 防重复提交；页面其它提交入口一并禁用。
- 单元格、下拉、小控件：允许 `Spin size="small"`，但必须紧邻可读文案，不能只转圈。
- 轮询与定时刷新：`silent` 刷新，不闪加载态、不清空已有内容。

### 3.3 禁止

- 纯文本单独充当加载指示器（「正在加载…」没有图形或骨架，慢网下会被当成空页）。
- 加载时清空已有数据，导致版面高度跳动。
- 同一区域同时出现骨架与转圈两套加载指示。

## 4. 空态

空态必须回答「为什么空 + 下一步做什么」，并区分三种来源：

| 类型 | 标题 | 描述 | 动作 |
| --- | --- | --- | --- |
| 从未使用 | 这里本该有什么 | 一句话说明用途 | 一个主动作（去创建 / 去上传） |
| 筛选无结果 | 没有符合条件的结果 | 建议放宽或清除筛选 | 清除筛选 |
| 小区域无内容 | 具体的空内容名称 | 可省略 | 可选 |

组件：

- C 端页面级：`StateEmpty`；工具结果栏：`ToolEmptyState`（含能力专属插画与流程步骤）。
- 后台：`EmptyState`；表格内置空态通过 `emptyText` / `emptyAction` 传入，不另写。
- 紧凑区域（通知面板等）：可用 `Empty`，但必须带 `description`。

禁止：

- 用空态表达失败或不可用。
- 空态只有插画没有标题。
- 空态文案复述界面（「暂无数据」单独出现不合格，必须说明这是什么区域）。

## 5. 失败

| 场景 | 表现 | 组件 |
| --- | --- | --- |
| 首屏失败、无旧数据 | 整块失败态 + 重试 | C 端 `StateError`；后台 `ListError` |
| 刷新失败、有旧数据 | 顶部提示条 + 保留数据 + 重试 | 后台 `StaleError`；C 端等价提示 |
| 操作失败 | Toast（错误 6 秒）或字段内联错误 | `message.error` / 表单错误 |
| 危险操作被拒 | 弹窗或内联提示 + 可执行下一步 | 参考退款错误码映射 [error-copy.md](error-copy.md) §4 |

规则：

- 失败态必须给「发生了什么 + 是否扣费 / 产出 + 下一步」；能重试才给重试按钮，点了没反应的按钮比没有更糟。
- 首屏失败不得渲染成空态；刷新失败不得清空旧数据。
- **C 端不展示原始报错与状态码**；后台可在详情中展示。请求号只在 5xx 时由请求层追加。
- 表单校验错误就地显示在字段下方，不用 Toast 代替。

## 6. 成功与提示

- Toast 时长固定：成功 4 秒、警示 5 秒、失败 6 秒；同时最多 4 条，超出挤掉最早一条。不要在调用处另设时长。
- Toast 只用于**瞬时反馈**（保存成功、复制成功、轻量校验）。需要用户确认或持续可见的结果（支付完成、批量结果、失败原因）用页面状态、结果卡或弹窗承载。
- 一次操作只给一次反馈：用了 Toast 就不再弹同义弹窗；按钮文案已表达结果时，Toast 不重复同一句话。
- 错误提示使用 `error`，不要用 `success` 伪装失败；同一操作连续触发时先去重。

## 7. 确认与阻塞

- 删除、退款、扣积分、调价、批量动作等不可逆或有业务后果的操作，必须二次确认。
- 确认内容包含：**动作 + 后果 + 是否可撤销**；危险按钮使用 danger 语义。
- 确认期间按钮进入 loading 并禁用，避免重复提交。
- 可恢复的失败不要用阻塞弹窗；用 Toast 或内联提示。

## 8. 可访问性

- 加载与状态变化区域使用 `aria-live="polite"`；错误使用 `role="alert"`；骨架区域可加 `aria-busy="true"`。
- 状态不能只靠颜色：必须同时有文字（`STATUS_META` 的双编码规则）。
- 装饰图标 `aria-hidden`；纯图标按钮必须有 `aria-label`。
- 弹窗打开后焦点进入弹窗，关闭后回到触发元素。

## 9. 组件取用

| 端 | 状态 | 唯一取用 |
| --- | --- | --- |
| C 端 | 骨架 / 行内加载 / 空 / 失败 | `components/StateViews.tsx` 的 `StateSkeleton` / `StateLoading` / `StateEmpty` / `StateError` |
| C 端 | 工具结果空态 / 生成中 | `components/ToolEmptyState.tsx` |
| C 端 | Toast / 确认 | `useApp()` 的 `message` / `modal` |
| 后台 | 页面骨架 | `primitives` 的 `PageSkeleton` / `SkeletonPanel` / `SkeletonBody` / `SkeletonStats` / `SkeletonCards` / `SkeletonTabs` |
| 后台 | 空 / 首屏失败 / 陈旧 | `primitives` 的 `EmptyState` / `ListError` / `StaleError` |
| 后台 | 状态标签 | `primitives` 的 `StatusTag` + `components/admin/statusMeta.ts` 的 `STATUS_META` |
| 后台 | Toast / 确认 | `ToastProvider` / `ConfirmProvider`（或 `useConfirm()`） |

新增页面不得另写一套「加载中 / 空 / 失败」；缺形态时先扩展上述组件，再接入页面。

## 10. 交付前自检

- [ ] 同一区域是否只出现一种状态？空、失败、不可用是否分清？
- [ ] 首屏加载是否占用真实布局，而不是清空版面？
- [ ] 提交后是否立即进入生成中，而不是退回空态？
- [ ] 失败文案是否说明了钱与产出，并给出可执行的下一步？
- [ ] 结果不明是否避免了重试诱导？
- [ ] 刷新失败是否保留了旧数据并明确标注「这是旧数据」？
- [ ] 是否只在瞬时反馈使用 Toast，且没有重复提示？
- [ ] 不可逆操作是否有二次确认与后果说明？
- [ ] 状态是否有文字而非只有颜色？加载与错误是否带 `aria-live` / `role`？

## 11. 已知缺口

- C 端多个页面把原始错误传给 `StateError` 的 `detail`（如 `WorkbenchDashboard` / `WorkbenchRecentPanel` / `ToolHistoryPane`），与「C 端不展示原始报错」冲突；后台不受影响。
- 仍有十余处直接使用 `Spin` 作为块级加载指示，未统一到 `StateLoading` / 骨架。
- C 端没有独立的「结果不明」组件，目前复用 `42206` 文案与失败卡。
- Toast 时长固定在 Provider 内，不支持按调用覆盖；超长错误在 6 秒内可能读不完。
- 任务 `queued` 与 `running` 在 C 端合并展示，用户无法判断是否已开始消耗上游资源（刻意取舍，非缺陷）。
