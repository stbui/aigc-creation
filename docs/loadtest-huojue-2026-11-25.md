# huojue 项目 HTTP 压测报告

- 日期：2026-11-25 ~ 26
- 目标机：`root@8.166.109.24`（阿里云 Ubuntu 26.04，2 vCPU / 3.7 GB）
- 被测服务：`/opt/huojue`，nginx `0.0.0.0:5100` → 静态前端 + 反代 `/api/`、`/uploads/` → NestJS `127.0.0.1:4100`；Redis `127.0.0.1:6379`
- 压测客户端：服务器本机 Node v22，HTTP keep-alive，凭据本地读取（不落对话、不回显）
- 端点范围：静态首页 + `/healthz` + 只读鉴权 API（`me` / `capabilities` / `admin/workbench`），**不写入业务数据**

## 1. 结论

服务在高强度压测下**零错误、零 5xx、零日志异常**，压测后健康探针正常。瓶颈**不在 nginx 或系统资源，而在 NestJS 后端鉴权路径**，表现为单线程 CPU 饱和：并发上升时 QPS 触顶、延迟线性增长。

## 2. 核心数据

### 2.1 高强度混合压测（并发 200 / 120s）

| 指标 | 值 |
| --- | --- |
| 总请求 | 80,044 |
| QPS | 664.4 |
| 错误 | 0（0%） |
| 延迟 P50 / P95 / P99 | 450.87 / 587.67 / 651.93 ms |
| 延迟 max | 864.64 ms |

分场景均延迟：静态首页 0.89ms、healthz 0.76ms、me 500.32ms、capabilities 499.76ms、admin/workbench 498.82ms —— 静态与动态接口相差约 500 倍。

| 场景 | QPS | P50 | P95 | 错误 |
| --- | --- | --- | --- | --- |
| 纯静态（`/` + `/healthz`） | 6,696.7 | 27.9ms | 44.16ms | 0 |
| 纯鉴权 API | 374.3 | 515.42ms | 681.34ms | 0 |

静态层与动态层吞吐相差 **约 18 倍**。

### 2.3 鉴权接口并发梯度（`/api/v1/me`，单独压）

| 并发 | QPS | P50 | P95 | 平均 |
| --- | --- | --- | --- | --- |
| 1 | 235.7 | 3.83ms | 6.14ms | 4.14ms |
| 10 | 320.4 | 30.38ms | 39.54ms | 31.07ms |
| 50 | 359.4 | 134.32ms | 168.05ms | 137.93ms |
| 200 | — | 515.42ms | 681.34ms | 524.91ms |

QPS 天花板约 **374**，延迟随并发近似线性增长（4 → 30 → 134 → 515ms），符合 Little's Law（N≈并发 / 平均响应时间），是典型的单进程串行处理饱和，而非错误或资源耗尽。

### 2.4 系统资源（120s 采样）

- 整机 CPU：68%~93%（含压测客户端与服务端同机争用）
- 内存占用：43%~45%，稳定无泄漏
- ESTAB 连接：约 800~1100，稳定
- Redis 连接：4~8，稳定；load average 约 2.1~2.9（2 vCPU，基本跑满）
- nginx error log：1 行（压测前后无变化）
- app error log：3 行（均为压测前的旧记录，压测期间无新增）
- 压测后：`/healthz` 200（0.25ms）、`/api/v1/me` 未带 token 401（鉴权守卫正常）

## 3. 瓶颈定位

1. **排除 nginx / 静态层**：纯静态 6,697 QPS、P50 28ms，静态资源直接由 nginx 返回，不构成瓶颈。
2. **排除系统资源**：内存稳定在 45%，无 OOM；磁盘 I/O、Redis 连接均无异常；错误日志零增长。
3. **锁定 NestJS 鉴权路径**：所有鉴权接口延迟高度一致（~500ms），且与并发线性相关；单并发仅 4ms，说明单次处理很快，瓶颈在**并发串行化**。
4. **根因推断**：Node 单进程事件循环 + SQLite/Prisma 单写者或同步段，导致 CPU 在约 374 QPS 处饱和；整机仅 2 vCPU，压测客户端与服务端同机进一步争用 CPU，可能使服务端实际上限被低估。

## 4. 建议（按优先级）

1. **分离压测机**：客户端与服务端同机会争用 2 vCPU，QPS 数字偏保守；正式验收应在独立机器发压。
2. **定位鉴权路径热点**：用 `node --cpu-prof` 或 clinic.js 抓取 `me` 接口 profile，确认是 JWT 校验、Prisma 查询还是序列化开销。
3. **横向扩展 / 集群**：若单进程上限确为 ~374 QPS，用 PM2 cluster 或容器多副本 + 上游负载均衡，可近线性提升。
4. **热点接口加缓存**：`capabilities` 响应体约 45KB 且为配置类数据，适合缓存到 Redis，可显著降低重复计算与 DB 压力。
5. **建立基线门禁**：将本报告的 QPS/延迟写入 `docs/testing.md` 的性能基线，后续改动对照，防止回归。
