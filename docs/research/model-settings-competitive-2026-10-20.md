# 市面产品「模型设置」调研

> 2026-10-20 · 为 aigc-creation 后台模型配置页重设计做参考
> 结论均来自官方文档或实测评测，标注了取证来源；无法证证的推测已明确标出。

---

## 一、按用途分成三类，不能混为一谈

调研中最容易被误导的地方，是把三类完全不同的「模型设置」放在一起比较。
它们的用户、频率、失败代价都不同，设计取向也就相反。

| 类型 | 代表 | 用户 | 设置频率 | 设计取向 |
|---|---|---|---|---|
| **A. 多厂商网关** | New API / One API | 运维 | 一次，长期不改 | **状态与健康度优先** |
| **B. 自定义接入** | Manus / Teable / PandaNpc | 集成方 | 一次，调试期反复 | **验证与排障优先** |
| **C. 消费级创作** | 即梦 / 可灵 / Liblib | 终端用户 | 每次生成 | **参数与成本前置** |

**我们后台属于 A**（多厂商网关）。C 类产品的做法**不能直接抄** ——
它们把模型选择放在创作流里，因为终端用户每次都要选；
而我们的配置是运维一次性设置、长期不管。

## 二、A 类：多厂商网关（New API，最贴近我们）

来源：[New API 官方文档 · Channel Management](https://docs.newapi.ai/en/docs/guide/feature-guide/admin/channel)

### 核心设计

1. **Channel（渠道）是核心配置单元**
   "each channel corresponds to one provider's API key"
   —— 一个渠道 = 一家供应商的一个 Key。这是**身份维度**的切分，
   与我们「一家厂商一条（含各模态通道）」的设计同构。

2. **列表页每行直接显示健康度**
   `name / type / status（绿=启用 红=停用）/ response time / used quota`
   —— 响应时间与已用额度是**列表列**，不是点进去才看。
   **我们的改造方向与之一致**（通道卡片并排、状态即入口）。

3. **「测试」是列表操作，不是详情页功能**
   操作列有 "Test" 按钮，另可 "Test All Channels" 批量测。
   我们的测试按钮在页头、针对当前模态 —— 少一个**批量测全部**。

4. **高级配置默认折叠**
   Base URL / Priority / Weight / Model Mapping / Parameter Override / Auto Disable
   —— 我们把「超时/轮询」12 项直接平铺，是可以收敛的。

5. **Auto Disable（连续失败自动停用）**
   我们没有这个能力。值得考虑，但**属于新功能**，不是 UI 重构。

### 它有而我们没有的

| 能力 | 价值 | 是否该抄 |
|---|---|---|
| 批量测试全部渠道 | 三模态 × 多厂商时手工点太慢 | **建议抄** —— 成本低 |
| 响应时间列 | 慢但可用 vs 快但超时，需要区分 | 需先有真实调用埋点 |
| Auto Disable | 防止坏渠道持续拖慢 | 需谨慎：自动停用可能掩盖问题 |
| Multi-Key 轮询 | 同渠道多 Key 容灾 | 与我们「令牌按模态分开」冲突，**不抄** |
| Priority / Weight | 多渠道负载均衡与灰度 | 未来多渠道时有用 |

## 三、B 类：自定义接入（集成方视角）

来源：[Manus 模型设置实操说明](https://blog.csdn.net/weixin_42515392/article/details/165111487)（第三方教程，但字段名经多篇交叉验证）、[Teable 自定义 AI 模型](https://help.teable.ai/zh/basic/ai/custom-model)、[PandaNpc 自定义供应商](https://pandanpc.com/docs/models/02-custom-providers)

### 高度一致的三个字段

三家都只让填 **Base URL / API Key / 模型** 三个核心项。
**没有**让人填完整端点路径 —— 因为拼错必然出错。

### 反复强调的坑（这些是我们应该在 UI 上预防的）

| 坑 | 出现次数 | 我们是否预防 |
|---|---|---|
| Base URL 末尾多写 `/v1` | 高频 | ✅ 已做（只存根域，provider 补版本段）|
| 把官网地址当 API 地址 | 中频 | ✅ 已做（存根域，非官网）|
| 模型 ID 凭印象填/抄旧教程 | **高频** | ✅ 已做（厂商预设给准确 ID）|
| 把登录密码当 API Key | 中频 | ❌ 未预防 |
| 改了 Key 留空 → 被清空 | 中频 | ✅ 已做（留空=保持原值）|

PandaNpc 有一条值得抄的原则：

> "Saving the record is not a connection test."
> **存好记录 ≠ 连通性已验证。**

对应我们的「测试连通性」按钮 —— 但我们把它放在页头、
**不强制先测就保存**。这一点与 New API 相同（都可跳过）。
考虑到我们的场景是生产关键路径，**保存前强制测一次**是值得讨论的加强项。

### 一个 B 类特有的关键点：区分「连通」与「能力匹配」

Teable 的做法很值得注意：

> "如果某个模型用于图片生成，请先勾选 **生图模型** 再执行测试。
> 勾选后会按生图模型测试**文生图**和**图生图**能力"

即：**测试方式必须与该模型的实际模态匹配**。
用文本测试去验一个生图模型，通过了也不说明它能用。

映射到我们：我们已有独立的「视频通道测试」，方向正确。
但**图像通道的测试目前只验连通，不验真实出图** ——
一个能连通的 openai 协议通道，若模型名填错（如填了不支持生图的模型），
测试会通过但生成必然失败。这是可补的缺口。

## 四、C 类：消费级创作（不可直接抄，但有可借鉴的信息呈现）

来源：[即梦](http://jimeng.jianying.com/)、[可灵 4.0 上手指南](http://omnitools.ai/article/kling-4-0-20-120)、[LiblibAI](https://www.liblib.art/)

### 关键特征

- **成本与参数前置到创作页**：分辨率 / 时长 / 画幅 / 模式，每个都有明确档位与积分价
- **成本焦虑是真实痛点**：多篇评测的核心主题是「单条成本」「隐藏成本」
  - 可灵：约 ¥0.45/条（标准版）
  - Runway：约 ¥3.5/条（折算）
  - 结论常写成「国产工具单条成本是它的零头」
- **参数是枚举而非自由输入**：分辨率 720p/1080p/4K、时长按秒递增
  —— 与我们视频能力用 `VIDEO_DURATIONS`/`VIDEO_RESOLUTIONS` 枚举的做法一致

### 唯一值得借鉴的一点

**「模式」的双档设计**（可灵：标准模式快 / 专业模式慢）本质是
**同一模型的两档质量×耗时**，比单纯的分辨率枚举更贴近用户决策。

对我们的启示：我们的能力参数里**缺少「质量档」这一维**。
图像侧目前只有比例与分辨率，运营实际关心的「先试跑还是正式出图」
没有被建模 —— 现有的 `route`（auto/local/remote）是路由而非质量档。

### 不该抄的

- 把模型选择放创作流：我们的用户是**运营**，一次配好长期用
- 用积分体系绑定模型选择：我们的计费已独立（`creditCost`），不与厂商耦合

## 五、对我们页面的具体结论

> **实施状态（2026-10-20 19:07 更新）**：第 1~5 项已落地。
> 实施时还查出一个**比第 5 项更严重**的缺陷（探测路径按模态硬编码），
> 详见 `docs/research/` 同目录的实现记录与 `verify-channel-test.ts` 断言。

| # | 结论 | 依据 | 状态 |
|---|---|---|---|
| 1 | **通道卡片并排、状态即入口** | New API 列表列健康度 | ✅ 已完成 |
| 2 | **路由总览按模态分组 + 无兜底计数** | 我们自己的三态改造 | ✅ 已完成 |
| 3 | **补「批量测试全部通道」按钮** | New API "Test All Channels" | ✅ 已完成（`POST /admin/model-config/test-all`，并发）|
| 4 | **高级配置默认折叠** | New API 高级配置折叠 | ✅ 已完成（「超时与轮询」9 项默认折叠，状态存 localStorage）|
| 5 | **通道测试须匹配模态 / 区分「可达」与「可用」** | Teable「测试方式须匹配模态」| ✅ 已完成（探测路径改由协议层派生 + 模型名校验 + 状态码分档）|
| 6 | **考虑保存前强制连通性测试** | PandaNpc「保存 ≠ 验证」| ⬜ 未做（生产关键路径，值得讨论）|
| 7 | 引入「质量档」维度（对应 route 而非分辨率） | 可灵标准/专业双档 | ⬜ 未做（需产品决策）|
| 8 | Auto Disable / 响应时间列 / Multi-Key | New API | ⬜ 未做（需先有调用埋点；Multi-Key 与现有设计冲突）|

### 实施时发现的额外缺陷（比第 5 项更严重）

原后台的连通性探测**按模态硬编码路径**：image 恒打 `/generation/tasks` ——
那是 **aigc 自研网关**的路径。而 5 个图像协议的真实端点各不相同：

```
aigc       → /generation/tasks
openai     → /v1/images/generations
volcengine → /images/generations
minimax    → /v1/image_generation
```

于是配了 `openai` 协议时，探测打的是优云智算/硅基流动**根本不存在**的路径，
拿到 404，而探测把 4xx 一律当「网络可达」→
**测试显示通过，但生成必然 404**。

这正是本报告第 5 点所说的「探测通过 ≠ 实际能调通」，
且与本项目最忌讳的「静默不实」完全一致 —— 运营看到绿色对勾，却每次生成都失败。

**修法**：探测路径改由**协议层**声明（与生成端点同源），不再有第二个真相源。
